# ADR 0003: 作業を終えたエージェントのロックと GitHub のマージ記録を確認する

ステータス: 採択

## 文脈

[ADR 0001](0001-worktree-cleanup.md) はロックされた worktree を保持する。
ロックは一時的に利用できないディスクを保護するためにも使われるが、エージェントが終了してもそのプロセスのロックが残る場合がある。
また、squash merge では PR がマージされても、元のブランチのコミットは基準ブランチの祖先にならない場合がある。
ロックの所有者が終了したかどうかと、作業が統合されたかどうかを独立に判定したい。

## 調査した事項

2026 年 11 月 11 日に `git -C ../peg-hs worktree list --porcelain` でロックを 8 件確認した。
全件の理由は `claude agent <登録名> (pid 74012 start Thu Nov  5 16:31:45 2026)` の形式だった。
同じ Mac の `LC_ALL=C ps -p 74012 -o pid=,lstart=` が返した開始日時は 11 月 11 日 09:44:36 で、ロックに記録された日時と異なった。
各作業ディレクトリで `git --no-optional-locks status --porcelain --ignored -unormal` を実行すると、全件に無視ファイルがあり、うち 3 件には追跡ファイルの変更もあった。
この 8 件は、所有者の終了を確認できても削除対象にはならない。

公開リポジトリ tett23/worktree-cleaner の PR #1 で、HEAD の完全なコミット ID を指定して `gh api repos/tett23/worktree-cleaner/commits/2f2463993cc65d77ac9574c365fb2a69118999e5/pulls` を実行した。
応答には PR 番号 1、空でない merged_at、head.sha と同じ指定コミット、base.repo.full_name、base.ref の main、マージコミット ID が含まれていた。
この実測例は通常のマージコミットを使った PR である。

## 実装すること

`--reclaim-agent-locks` は、この Mac で作成された自分専用のローカル worktree を対象に、認識できる Claude エージェントのロックを調べる。
指定する利用者は、対象が同じホストと PID 名前空間で管理され、ほかのプロセスが対象を使用したりロックを取り直したりしないことを確認する。
ロック理由にはホスト識別子がないため、共有ディレクトリ、コピー、別ホストから移した登録は対象にできない。
初版の所有者判定は調査した macOS の形式に限定する。

`--github-merged` はローカルで祖先判定が成立しなかった場合に、オプションの外部コマンド gh を起動して GitHub.com のマージ記録を問い合わせる。
両オプションとも一覧表示と削除で使え、片方だけでも指定できる。
例えば `worktree-cleaner --reclaim-agent-locks --github-merged` は候補と理由を表示する。
同じコマンドに `--remove-all` または `--remove PATH` を加えた場合だけ削除する。
ロック付き候補の理由には元のロック理由と所有者判定の根拠を、GitHub で確認した候補には PR の URL を表示する。

## アルゴリズム

### ロックの所有者と解除

登録が有効で作業ディレクトリが存在し、ロック理由の全文が上記の形式に一致し、登録名も一致する場合だけ PID と開始日時を読む。
PID は正の十進整数に限る。
同一ホストのプロセス表でその PID が存在しないと確認できた場合、または現在のプロセスが記録日時より後に開始したと確定できた場合に所有者終了と判定する。
PID 不在の根拠には同一ホストでの kill(pid, 0) の ESRCH を使う。
ps の空出力や終了コードだけからは不在と判断しない。
照会の失敗、権限不足、日時の解釈の不一致や不明なタイムゾーンは保持とする。
PID の存在だけ、経過日数だけ、ブランチ名だけでは解除しない。

削除候補を調べる間はロックを維持する。
統合の確認には、従来のローカル祖先判定か、この ADR で定める GitHub の証拠を使う。
ローカルブランチに接続した HEAD で、[ADR 0001](0001-worktree-cleanup.md) の登録、現在地、基準ブランチ自身、clean 判定など残りの保護条件もすべて満たした場合だけ、解除可能な候補とする。
削除直前に登録、パス、ブランチ、HEAD、ロック理由のバイト列、所有者終了、統合状態、保護条件を再検査する。
今回の初回判定と対象またはロックが変わっていればスキップする。
解除直後にも登録と保護条件を確認し、再ロックがあれば保持する。
削除にはロックを無視する prune フラグを使わない。
解除後に削除できず同じ登録が残った場合は、他者のロックを上書きせず元の理由で再ロックする。
削除失敗時に部分削除、再ロック失敗、登録の消失を検出した場合は対象パスと復旧結果を報告して異常終了する。

### GitHub による統合の確認

ローカルの基準ブランチを解決し、ローカルブランチ上の HEAD がその祖先ではないと確定した場合にだけ問い合わせる。
先に clean 判定などのローカル検査を通し、保持が決まっている対象についての通信を省く。
origin の URL から github.com の owner と repository を抽出し、HTTPS または SSH の既知形式以外は保持する。
`gh api --hostname github.com` に固定したホスト、検証済みのリポジトリ識別子、完全な HEAD コミット ID を引数として渡し、関連 PR をページ末尾まで読む。
gh の構造化フィールド抽出を使い、シェル展開や追加の Rust クレートを必要としない。

採用する証拠は、一つの PR の merged_at が存在し、head.sha が現在の HEAD と一致し、base.repo と base.ref がそれぞれ origin のリポジトリと今回の基準ブランチに一致することである。
さらに、その PR の merge_commit_sha がローカルの基準先端と同一か祖先であることを libgit2 で確認する。
これにより、同名ブランチへの追加コミットや、ローカルの基準に届いていないマージを削除の根拠から除く。
GitHub による候補の削除直前には再照会し、同じ PR とコミットについて条件が成立することを確認する。
認証エラー、タイムアウト、レート制限、不完全な応答は理由を示して保持し、ローカルで判定できるほかの対象を処理する。

## 実装しないこと

理由のないロック、手動ロック、未知のエージェントのロックは解除しない。
fetch、push、PR の変更、ロック解除だけを行うコマンドは対象外とする。
[ADR 0002](0002-include-unmerged-worktrees.md) の未マージ候補を選ぶ指定は、ロック付き worktree の統合確認を代替しない。

## 不変条件

1. 明示的な GitHub オプションのない実行は gh を起動せず、通信しない。
2. 一覧表示では、どのオプションの組合せでもロック理由、登録、作業ファイル、参照を変更しない。
3. ロック付き worktree は、解除オプション、所有者終了、統合確認、その他の保護条件のすべてが成立した場合だけ削除対象となる。
4. GitHub の情報だけで祖先判定を補う場合、同じ PR が上記の全条件を満たす場合だけ候補となる。
5. 再検査で前提が崩れた場合は削除しない。
6. 解除後の失敗で同じ登録が残った場合には、既存ロックを保持するか、元の理由を復元し、復元できなければ失敗を報告する。

| 境界の入力（ほかの条件は成立） | 結果 |
| --- | --- |
| 所有者の PID と開始時刻が一致 | ロックを保持 |
| PID が再利用され、新しいプロセスの開始を確認 | 解除オプションありなら候補 |
| 終了を確認したが無視ファイルが一つある | 元のロックのまま保持 |
| squash マージ済みで PR の HEAD と現在の HEAD が一致 | GitHub オプションありなら候補 |
| マージ後に一つコミットを追加 | その PR では保持 |
| 同じコミットの PR が別の基準ブランチにマージされた | その PR では保持 |
| API の途中ページの取得に失敗 | GitHub 判定では保持 |

## テスト設計

各テスト名に不変条件番号を含める。
条件 1 と 4 は偽の gh で呼び出し回数と引数を記録し、通常マージ、squash、rebase 後のコミットグラフを一時リポジトリで作る。
未マージ、別リポジトリ、HEAD の不一致、別の基準、ローカル基準の遅れ、ページング、通信失敗を個別に試す。
条件 2 と 3 は一時 worktree に理由付きロックを設定し、プロセス照会結果を差し替えて境界表、PID 不在、権限不足、形式不一致を検証する。
条件 5 と 6 は候補選択後の HEAD 更新、ロック理由の変更、解除直後の再ロック、削除失敗、復元失敗をそれぞれ再現し、ファイル、登録、理由、終了コードを確認する。

## トレードオフ

PID と記録日時だけでは、別ホストの所有者や同じディレクトリで新たに作業する人を特定できない。
また、理由の再検査とロック解除の間にも競合の余地があり、その間に他者が取得し直したロックを識別できない。
ロックの復旧を含む不変条件は、前述の同時操作を止める前提のもとで適用する。
そのため利用環境の前提を満たせない場合はロックを保持する。
GitHub の証拠が示すのはその先端の PR が指定先にマージされた履歴であり、競合解消や後続の revert を経た現在のファイル内容の同一性は保証しない。
GitHub 照会はローカルの基準が古い場合や gh が使えない場合に候補を取りこぼすが、その場でリモートやローカル参照を更新する必要がない。
