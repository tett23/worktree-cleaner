# ADR 0001: マージ済みの worktree を整理する

ステータス: 採択

## 文脈

Git の linked worktree は、一つのリポジトリで複数の作業ディレクトリを使うための仕組みである。
最終更新日時だけでは、作業を終えたかどうかを判断できない。
利用者が統合先と判断したローカルブランチを基準に、作業を失わずに片付けられる候補を探したい。

## 実装すること

探索の起点は `--root <ディレクトリ>` で指定し、省略時はカレントディレクトリを使う。
起点が主 worktree または linked worktree の内部（ルートを含む）なら、そのリポジトリだけを調べる。
それ以外の場合は、直下にある主 worktree ごとに Git の登録を読み、そのリポジトリに属する linked worktree を調べる。
登録された linked worktree は、起点の外に置かれていても対象に含む。

基準ブランチはリポジトリごとに決める。
既定ではローカルに記録された origin/HEAD の参照先（例では origin/main）から対応するローカルブランチ（main）を求める。
`--base <名前>` を指定した場合は、各リポジトリでその名前のローカルブランチを使う。
基準を特定できないリポジトリは理由を表示して保持し、残りのリポジトリの処理を続ける。
既定の操作では各 worktree のパスと、候補または保持とした理由を表示する。
削除範囲は `--remove <worktree のパス>` で一件、または `--remove-all` で今回の探索で見つかった候補すべてを指定する。
単一指定でも今回の探索で見つけた候補だけを削除対象とする。
一覧のリポジトリ名には主 worktree のディレクトリ名を使う。
たとえば `tett23` ディレクトリで `worktree-cleaner` を実行すると、リポジトリ名、worktree の絶対パス、判定理由が一覧に出る。
同じ場所で `worktree-cleaner --remove-all` を実行すると、各候補を削除直前に再検査して整理する。
Rust の標準ライブラリからシステムの libgit2 を呼ぶ。

## 実装しないこと

ブランチの削除、リモートとの通信、強制削除、存在しない作業ディレクトリの登録解除は対象外とする。

## 不変条件

1. 作業ディレクトリを開き直し、登録と同じリポジトリの同じ linked worktree と確認できるものだけを候補にする。
2. ロックされた worktree を保持する。
3. 実行時のカレントディレクトリの実体を含む worktree を保持する。
4. 基準ブランチ自身を保持する。
5. HEAD がローカルブランチを指し、そのコミットが基準の先端と同一か祖先である場合だけを候補にする。
6. インデックスまたは追跡ファイルに変更があれば保持する。
7. 未追跡ファイルは無視設定にかかわらず保持する。
8. 入れ子のリポジトリまたはサブモジュールがあれば保持する。
9. libgit2 の git_repository_state が GIT_REPOSITORY_STATE_NONE 以外を返す場合は保持する。
10. いずれかの検査に失敗した worktree を保持する。
11. 一覧操作ではファイル、登録、ブランチ参照を変更しない。
12. 削除操作では指定範囲の各候補について条件 1 から 10 を直前に再検査し、候補である場合に限り作業ディレクトリと登録を削除する。
13. 削除操作はすべてのブランチ参照を保持する。
14. 親ディレクトリからは直下の実ディレクトリにある主 worktree だけを探索の入口とする。シンボリックリンクをたどらず、子孫を再帰探索しない。
15. 各候補の到達可能性は、その候補が属するリポジトリの基準ブランチについて判定する。
16. 一つのリポジトリで基準の解決に失敗しても、ほかのリポジトリを処理する。

ほかの条件をすべて満たす場合の境界を示す。

| 入力 | 結果 |
| --- | --- |
| linked worktree がない | 候補は空 |
| 別ブランチが基準と同じコミットを指す | 候補 |
| 基準から到達できないコミットが一つある | 保持 |
| 無視ファイルが一つある | 保持 |
| 一覧の後にロックされた | 削除を拒否 |
| 直下にリポジトリがない | 候補は空 |
| 二つのリポジトリのうち一方だけに基準がある | 基準がある側の候補だけを整理 |
| 直下のリポジトリが起点外に worktree を登録している | 登録先を通常どおり判定 |

## テスト設計

一時リポジトリを作り、テスト名に対応する不変条件の番号を入れる。
条件 1 から 4 は主 worktree、壊れた登録、ロック、現在地の親、基準ブランチを個別に試す。
条件 5 は同じ先端、祖先、分岐、detached HEAD を試す。
条件 6 から 10 は各除外条件を一つずつ作り、ステージ済みの変更だけがある場合も保持を確かめる。
条件 11 から 13 は一覧前後の状態、一覧後の変更による拒否、削除後の登録、残ったブランチと隣接 worktree の内容を確かめる。

条件 14 から 16 は一時ディレクトリの直下に main と master をそれぞれ基準とする二つのリポジトリを置き、起点内からの実行と外からの `--root` 指定で同じ候補が出ることを確かめる。
起点外の登録先、シンボリックリンク、孫のリポジトリ、基準を解決できないリポジトリを加え、探索範囲と結果を確認する。
条件 12 の一括削除では二件の候補の一方を再検査前に変更し、もう一方だけが削除されることを確認する。

## トレードオフ

squash merge や rebase でコミット ID が変わると、内容が統合済みでも候補から外れる。
無視されたビルド成果物も保持するため、再生成できるファイルは利用者が先に片付ける。
削除直前の再検査とファイル削除は不可分ではないため、削除中は対象での並行作業を止める必要がある。
